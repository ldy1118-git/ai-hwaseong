## 1. 오프닝 — 문제 정의 (2분)

### 발표 문구

> "화성시 소상공인은 지원사업을 알아도, 신청하지 못합니다."

소상공인이 지원사업을 놓치는 이유는 정보 부족이 아닙니다.  
공고문이 길고 복잡하고, 자격 조건이 행정 용어로 가득 차 있고, 어떤 서류를 어디서 발급받는지 파악하는 데 시간이 너무 많이 걸립니다.

**구체적 Pain Point 3가지:**

| 문제 | 현실 |
|---|---|
| ① 조건 해석 | "중위소득 120% 이하"가 나에게 해당하는지 모름 |
| ② 공고문 독해 | 지원금 금액, 마감일, 자격이 여러 페이지에 흩어져 있음 |
| ③ 서류 발급 | 사업자등록증명과 사업자등록증이 다른 서류인지도 모름 |

**우리의 질문:**  
AI가 "사람 대신 읽고, 조건을 확인하고, 서류 준비를 도와주면" 어떨까?

## 2. 서비스 개요 — 4개 기능 (3분)

### 아키텍처 전체 흐름도

```
사용자 입력 (자유 텍스트)
        │
        ▼
  [기능1] 조건 해석 ──── LLM ────► 구조화 프로필 JSON
        │
        ▼
  [매칭엔진] 지원사업 매칭 ────────► 매칭 결과 JSON
        │
        ├──► [기능2-a] 공고문 요약 ── LLM ──► 요약 JSON (만료 판정 포함)
        │
        └──► [기능2-b] 서류 체크리스트 ── LLM + RAG ──► 서류별 발급처·URL·주의사항
        
  [기능3] 챗봇 ── LLM + RAG ──► 멀티턴 대화 (용어 설명, 서류 안내, 상권 정보)
```

**기능별 한 줄 요약:**

| 기능 | 설명 | 핵심 기술 |
|---|---|---|
| **기능1** 조건 해석 | "기초생활수급자, 화성시 카페 창업"→ 구조화 JSON | LLM 단독 |
| **기능2-a** 공고문 요약 | 긴 공고문→ 핵심 요약 + 만료 여부 | LLM 단독 |
| **기능2-b** 서류 체크리스트 | 매칭 결과→ 서류별 발급처·URL 안내 | LLM + **RAG** |
| **기능3** 챗봇 | 세무·지원사업·상권 질문 멀티턴 응답 | LLM + **RAG** |

## 3. 기능1 — 조건 해석 기술 설명 (3분)

### "왜 LLM으로 파싱했나?"

소상공인이 입력하는 문장은 구조가 없습니다.

> "화성시 향남읍에서 카페 창업 준비 중인 만 29세, 창업 경험 없음, 기초생활수급자입니다."

이것을 정규식으로 파싱하면 수백 가지 케이스 처리가 필요합니다.  
LLM은 한 번의 프롬프트로 아래를 동시에 처리합니다.

```json
{
  "age": 29,
  "region": "화성시 향남읍",
  "business_type": "카페",
  "startup_stage": "예비창업자",
  "career_experience": "없음",
  "income_level": "기초생활수급자"
}
```

### 함정 케이스에서 검증한 것

단순히 잘 파싱하는 것이 목표가 아닙니다. **"모르면 모른다고 해야 한다"** 가 핵심입니다.

| 테스트 케이스 | 입력의 함정 | 올바른 처리 |
|---|---|---|
| F1-02 | 자산 상태 미입력 | `asset_status: null` + `missing_info` 반환 |
| F1-03 | "프리랜서" (비매핑 업종) | `business_type: "기타"` + `warnings` 반환 |
| F1-04 | "조금 있어요" (모호한 경력) | `career_experience: "ambiguous"` 처리 |
| F1-06 | 사업자등록 여부 미입력 | 매칭에 영향을 주는 필드임을 `uncollected`로 표시 |

**결과: 6/6 PASS**  
누락·모호·비매핑 케이스 모두 안전하게 처리. 매칭엔진으로 잘못된 값이 흘러가지 않음.

### 기술 선택 포인트

- `temperature=0`: 같은 입력에 항상 같은 출력 (재현 가능성 확보)
- `JSON 강제 출력`: 다운스트림 매칭엔진이 파싱 오류 없이 소비 가능
- `null 규율`: "모름"을 빈 문자열이나 설명 텍스트로 채우지 않음 → 타입 안전성 확보

## 4. 기능2-a — 공고문 요약 기술 설명 (2분)

### baseline vs v1의 결정적 차이

**F2A-04 — 만료 공고 판정 실패 (baseline) vs 성공 (v1)**

공고 마감일: `2026-02-28`  
오늘 날짜: `2026-08-15`

| | baseline | v1 |
|---|---|---|
| `is_expired` | **false** ← 오답 | **true** ← 정답 |
| 원인 | LLM이 날짜 기준 없이 판단 | 시스템 프롬프트에 오늘 날짜 주입 |

> 만료된 공고를 "아직 신청 가능"으로 보여주면 소상공인이 헛걸음하게 됩니다.  
> v1은 **현재 날짜를 프롬프트에 명시**하여 이 문제를 해결합니다.

### Null 규율의 중요성

baseline은 null이어야 할 필드에 설명 텍스트를 채웁니다.

```json
// baseline — 잘못된 처리
"support_amount": "본문 내용 절단으로 인해 구체적인 금액 미기재"

// v1 — 올바른 처리
"support_amount": null,
"missing_info": ["support_amount"]
```

후자만이 매칭엔진에서 `if (support_amount === null)` 체크가 가능합니다.  
**"모름"을 null로 표현하는 것이 API 설계의 기본이고, 이를 LLM이 지키게 만드는 것이 프롬프트 엔지니어링의 핵심입니다.**

## 5. 기능3 챗봇 RAG — 핵심 기술 결정 (6분)

> 이 섹션이 발표의 기술적 하이라이트입니다. 숫자와 대비를 최대한 활용하세요.

### 5-1. RAG란 무엇인가, 왜 필요한가

LLM은 학습 데이터에 없는 정보는 만들어냅니다(환각). 화성시 특유의 지원사업 정보, 소상공인 행정 용어, 서류 발급처 URL은 LLM이 정확히 알 수 없습니다.

**RAG(Retrieval-Augmented Generation)**: 질문이 들어오면 관련 문서를 검색해 LLM 프롬프트에 "문서를 찍어 주는" 방식.

```
질문: "이차보전이 뭐예요?"
        │
        ▼
[검색] terms.json에서 "이차보전" 항목 검색
        │
        ▼
[주입] LLM 프롬프트에 용어 정의 + 주의사항 + URL 삽입
        │
        ▼
[생성] LLM이 주입된 정보를 근거로 답변
```

### 5-2. 환각 억제 — 가장 중요한 실험 결과

**F3-03: "화성시 소상공인 자금지원사업 금리가 정확히 몇 %예요?"**  
→ terms.json에 금리 정보가 없음 → RAG 컨텍스트 없음 → LLM이 어떻게 반응하는가?

| | baseline (RAG 없음) | v1 (키워드 RAG) |
|---|---|---|
| 답변 | **"금리는 연 1.5%입니다."** | "공고 또는 담당 기관에 확인 필요" |
| 문제 | 없는 정보를 자신 있게 답변 | 없으면 없다고 안내 |
| confidence | 표시 없음 | `low` 명시 |

> baseline이 생성한 "연 1.5%"는 완전한 환각입니다. 소상공인이 이 숫자를 믿고 자금 계획을 짰다가 실제 금리가 다르면 직접적인 피해가 됩니다.  
> **RAG는 정보를 추가하는 것뿐만 아니라, 없는 정보를 만들지 않도록 막는 역할을 합니다.**

### 5-3. URL 제공 효과

같은 LLM, 같은 질문 — RAG 유무만 다름.

| 지표 | baseline | v1 (키워드 RAG) |
|---|---|---|
| URL 포함 케이스 | **0/5** | **4/5** |
| 발급처 정확도 | 부정확 또는 누락 | RAG 기반 정확 |
| 미검증 경고 | 없음 | ⚠ 미검증 항목 자동 경고 |

**BM-02 중소기업확인서 사례:**
- baseline: "중소기업중앙회 www.smba.go.kr" → **잘못된 URL**
- v1: "중소기업현황정보시스템 https://sminfo.mss.go.kr" → **정확한 URL**

## 6. RAG 방식 선택 — 키워드 vs 임베딩 비교 (4분)

### "임베딩이 더 좋은 것 아닌가?" 라는 질문에 대한 답

일반적으로 임베딩(벡터 유사도) 검색이 더 발전된 방식으로 알려져 있습니다.  
우리는 두 방식을 **동일한 LLM, 동일한 5개 질문**으로 직접 비교했습니다.

### 검색 정확도 비교 (Hit@1: 정답이 1위에 검색된 비율)

| RAG 방식 | Hit@1 | Hit@3 | MRR | F3 PASS | 코퍼스 인코딩 |
|---|---|---|---|---|---|
| **키워드 substring** | **1.000** | **1.000** | **1.000** | **4/5** | 0ms |
| BGE-M3 임베딩 | 0.800 | 1.000 | 0.900 | 3/5 | 2,129ms |
| KoSimCSE-RoBERTa | 0.800 | 0.800 | 0.800 | — | 172ms |
| KR-SBERT | 0.800 | 0.800 | 0.800 | — | 158ms |

### 왜 이런 결과가 나왔나 — F3-03 핵심 분석

**질문:** "화성시 소상공인 자금지원사업 금리가 정확히 몇 %예요?"

| | 키워드 RAG | BGE-M3 RAG |
|---|---|---|
| 1위 검색 결과 | `소상공인` (용어 직접 매칭) | `미소금융` (의미 유사도 높음) |
| LLM에 주입된 컨텍스트 | 소상공인 정의, 융자 용어 | 미소금융 정의 + **금리 정보 있음** |
| LLM 답변 | "확인 필요" ← 억제 성공 | **"1.5%~3.5%"** ← 환각 발생 |

> "소상공인 자금지원 금리" → 임베딩이 의미상 가장 유사한 "미소금융"을 검색 → 미소금융 항목에는 금리 정보가 있음 → LLM이 해당 금리를 화성시 사업 금리로 오용.
>
> 키워드는 "소상공인"이라는 단어를 직접 매칭해 올바른 용어를 반환하고, 금리 정보가 없으면 없는 대로 답변.

### 결론: 코퍼스 크기가 RAG 방식 선택에 핵심

| 상황 | 적합한 방식 | 이유 |
|---|---|---|
| 소규모 전문 용어 코퍼스 (현재: 57개) | **키워드** | 용어가 질문에 직접 등장, 동의어 적음 |
| 대규모 자유 텍스트 코퍼스 (2차: 수천 개) | **임베딩 (BGE-M3)** | 우회 표현, 동의어 질문 증가 |

**현재 1차 서비스에서는 키워드 RAG가 더 안전하고 빠릅니다.**  
2차 개발에서 코퍼스를 확장하면 BGE-M3로 전환하는 계획이 이미 준비되어 있습니다.

## 7. LLM 선택 — Groq 채택 근거 (3분)

### 처음에는 Gemini를 썼다

초기 구현은 Google의 Gemini API(`gemini-3.6-flash`)로 시작했습니다.  
개발이 진행되면서 두 가지 문제가 드러났습니다.

1. **무료 플랜 일일 한도**: 20 req/day → 벤치마크 테스트 중 쿼터 소진, 다음 날까지 대기
2. **모델명 불안정**: `gemini-2.5-flash`가 이 API 키 형식으로 404 반환 → 버전 추적 어려움

### Groq으로 전환한 이유

| 항목 | Gemini (무료) | Groq (무료) |
|---|---|---|
| 일일 한도 | 20 req/day | **14,400 req/day** |
| 모델 | gemini-3.6-flash | llama-3.3-70b-versatile |
| 지연 시간 | 보통 | **빠름** (LPU 하드웨어) |
| 비용 | 무료 | **무료** |
| 재현성 | temperature=0 지원 | temperature=0 지원 |

Groq는 Meta의 LLaMA 3.3 70B 모델을 자체 LPU(Language Processing Unit) 하드웨어로 구동해 매우 빠른 응답 속도를 제공합니다. 무료 플랜에서도 하루 14,400 요청이 가능해 벤치마크와 서비스 모두 커버할 수 있었습니다.

### 통합 레이어: llmProvider.js

Gemini와 Groq를 동시에 지원하는 공통 래퍼를 만들었습니다.

```javascript
// src/utils/llmProvider.js
export async function generateText({
  provider = 'groq',  // 'gemini' | 'groq'
  apiKey, model, systemPrompt, userPrompt,
  jsonMode, history,
})
```

이 구조 덕분에 모든 기능(기능1~3)이 `provider` 파라미터 하나만 바꿔 어떤 LLM으로도 실행 가능합니다.  
**벤치마크 비교 가능, 프로덕션 전환 용이, 미래 모델 교체에도 코드 변경 최소화.**

## 8. 로컬 모델 비교 — Qwen2.5-7B (2분)

"비용 없이 완전히 온프레미스로 구동할 수 있는가?"를 검증하기 위해 Ollama로 로컬 모델을 테스트했습니다.

### 결과 요약 (F3 5케이스, Qwen2.5-7B vs Groq LLaMA-3.3-70B)

| 지표 | Groq LLaMA-3.3-70B | Qwen2.5-7B (로컬) |
|---|---|---|
| 환각 억제 (F3-03) | ✅ | ✅ (baseline도 환각 없음) |
| URL 포함률 | **4/5** | 1~2/5 |
| 프롬프트 지시 이행 (미검증 경고 등) | ✅ | ⚠ 미흡 |
| 추론 속도 | 빠름 (LPU) | 느림 (CPU/GPU) |
| 인프라 | 없음 (API) | 서버 필요 |

**핵심 발견**: Qwen2.5-7B는 환각 억제 면에서는 우수하지만, 구체적인 프롬프트 지시(URL 반드시 포함, 미검증 경고 문구 등)를 이행하는 능력이 70B 모델보다 낮습니다. 실서비스 사용자에게는 URL 하나의 차이가 실질적인 도움의 차이입니다.

**1차 서비스: Groq 유지. 2차에서 로컬 모델 재평가 (서버 확보 후).**

## 9. 기능2-b — 서류 체크리스트 RAG (2분)

### 서류 정보를 LLM이 알 수 없는 이유

"사업자등록증명은 어디서 발급받나요?"라고 물으면 LLM은 대략적인 답을 합니다.  
그러나 발급 URL, 소요시간, 수수료, 주의사항을 **정확하게** 알기는 어렵습니다.

### buildDocumentRAG()의 구조

공고문에서 요구 서류 이름이 나오면, `terms.json`의 `documents[]` 에서 해당 서류 정보를 찾아 LLM에 주입합니다.

```
공고 서류 목록: ["사업자등록증명", "중소기업확인서", ...]
        │
        ▼
buildDocumentRAG() → 서류명 + aliases로 terms.json 검색
        │
        ▼
매칭된 서류 정보 주입:
  - 발급 URL (sminfo.mss.go.kr)
  - 소요 시간 (즉시)
  - 수수료 (무료)
  - 주의사항 (재무제표 필요할 수 있음)
        │
        ▼
LLM이 서류별 체크리스트 생성
```

### 핵심 수치

| 항목 | 결과 |
|---|---|
| RAG 매칭률 | **100%** (14개 서류 전부 매칭) |
| URL 포함 (baseline 0개 → v1) | **4개 URL 자동 포함** |
| aliases 매칭 | `사업자등록증명원` → `사업자등록증명` 정확 매칭 |
| `verified=false` 서류 | `verify_note` 자동 생성 (⚠ 미확인 항목 표시) |

## 10. 프론트엔드 아키텍처 (2분)

### JupyterHub 환경 제약과 설계 결정

이 서비스는 JupyterHub 환경에서 서빙됩니다. 여기서 중요한 제약이 생깁니다.

**BrowserRouter를 쓰면 왜 안 되나:**
- JupyterHub는 `/user/{username}/proxy/3002/` 처럼 경로 앞에 prefix가 붙음
- BrowserRouter는 URL 경로를 직접 서버에 요청 → 프록시 환경에서 404 발생

**HashRouter를 선택한 이유:**
- URL이 `/#/dashboard` 형태 → `#` 이후는 서버에 전달되지 않음
- 정적 파일 서버(python http.server)가 항상 `index.html`만 반환하면 됨
- 어떤 경로로 진입해도 React가 내부적으로 라우팅 처리

```
일반: /dashboard → 서버에서 dashboard 경로 찾기 → 404
Hash: /#/dashboard → 서버는 / 만 봄 → index.html 반환 → React가 #/dashboard 처리
```

### 빌드 및 배포 구조

```bash
npm run build              # Vite로 번들링 → dist/
fuser -k 3002/tcp          # 기존 서버 종료
python3 -m http.server 3002 --directory dist &  # 정적 서빙
```

`npm run dev`(개발 서버)는 사용하지 않습니다 — JupyterHub 프록시와 웹소켓 충돌이 발생하기 때문입니다.

### API 키 처리

Groq API 키는 `.env` 파일에 `VITE_GROQ_API_KEY`로 관리합니다. Vite 빌드 시 번들에 포함되므로, 이 키는 **가역적으로 추출 가능**합니다. 따라서 실제 민감한 비즈니스 로직은 클라이언트에 두지 않고, API 요청 자체가 노출되어도 서비스에 영향 없는 수준(무료 API 키)만 사용합니다. **2차 개발에서 백엔드 API를 통해 키를 서버 측으로 이동할 예정입니다.**

## 11. 챗봇 프론트엔드 구현 (2분)

### RAG 챗봇 연결 구조

```javascript
// Chatbot.jsx 핵심 흐름
const result = await generateChatbotResponseV1(
  text,       // 사용자 입력
  history,    // 이전 대화 [{role, text}, ...]
  termsData,  // terms.json (57개 항목)
  GROQ_KEY,   // Groq API 키
  'groq'      // provider

// result 구조
{
  answer: "이차보전은 ...",          // 답변 텍스트
  confidence: "high",               // 신뢰도
  retrieved_terms: ["이차보전"],     // 사용한 용어
  retrieved_docs: [],               // 사용한 서류
  followup: ["신청 절차는?", ...]   // 후속 질문 제안
}
```

### UI 설계 결정

**followup 버튼을 답변 아래에 표시하는 이유:**  
소상공인이 다음에 무엇을 물어야 할지 모르는 상황을 줄이기 위해, AI가 직접 후속 질문을 제안합니다. 이는 대화의 맥락을 유지하면서 더 깊은 정보 탐색을 유도합니다.

**history 관리를 수동으로 하는 이유:**  
Gemini SDK의 `chat.startChat()` 대신 `messages` 배열을 직접 관리합니다. 이유:
1. Groq API는 OpenAI 호환 형식 — 히스토리를 배열로 직접 전달해야 함
2. 어떤 LLM provider를 쓰더라도 동일한 히스토리 구조를 유지할 수 있음
3. 히스토리에서 시스템 메시지(초기 인사말)를 명확히 제외할 수 있음

## 15. 마무리 메시지 (1분)

> "우리가 선택한 모든 기술에는 이유가 있습니다."

- Groq를 쓴 것: 20req vs 14,400req — 숫자로 증명
- 키워드 RAG를 쓴 것: Hit@1 1.0 vs 0.8, 환각 F3-03 — 실험으로 증명

**화성시 소상공인이 지원사업을 놓치지 않도록. 숫자로 검증된 AI 경영동행 서비스.**

## 부록: 자주 나올 질문 (Q&A 대비)

**Q. 온보딩에서 나이·창업경험·자산구간·결혼여부까지 묻던데, 그게 매칭에 쓰이나요?**
A. 지금 수집된 화성시 공고 27건에서는 안 쓰입니다. 27건이 거는 조건을 세어보면 운영여부 7건, 지역 3건, 업종 1건, 업력 1건, 매출 1건이고 나머지 14건은 요건 확인이 필요한 공고입니다. 나이·자산구간 같은 조건을 거는 공고가 이 27건 안에는 없습니다.
그럼에도 묻는 이유는, 이 필드들이 청년창업·저소득층 대상 사업에서 표준적으로 쓰이는 조건이기 때문입니다. 매칭 엔진은 이미 이 조건들을 판정할 수 있게 만들어져 있고(`min_age`/`max_age`/`asset_groups` 등 12개 키), 경기도·중소벤처기업부 공고로 범위를 넓히면 수집 다음 날부터 바로 걸립니다. 스키마를 먼저 잡고 데이터를 나중에 채우는 순서로 갔습니다.
반대로 답을 비워두는 것도 안전합니다. 스킵한 항목은 '불충족'이 아니라 '확인필요'로 처리해서, 모른다는 이유로 대상에서 빼지 않습니다.

**Q. Gemini 대신 Groq를 쓰면 한국어 성능이 떨어지지 않나요?**  
A. LLaMA 3.3 70B는 한국어 벤치마크에서 Gemini 2.5 Flash와 비슷한 수준입니다. 저희 F1~F3 테스트에서도 동등한 성능을 확인했으며, 오히려 JSON 지시 이행(null 규율, URL 포함 등)에서 더 일관된 결과를 보였습니다.

**Q. RAG 데이터(terms.json)는 어떻게 만들었나요?**  
A. 화성시 소상공인 지원사업 공고문, 국세청·소진공 행정 용어집을 수작업으로 정리했습니다. 현재 용어 31개 + 서류 26개(총 57개). 2차에서 공공데이터 API와 연동해 자동 갱신할 계획입니다.

**Q. 왜 임베딩 검색이 아닌 키워드를 선택했나요? 임베딩이 더 발전된 기술 아닌가요?**  
A. 발전된 기술이 항상 더 좋은 것은 아닙니다. 현재 코퍼스는 57개의 전문 용어 중심이고, 사용자 질문에 용어가 직접 등장하는 경우가 대부분입니다. 이 조건에서 키워드가 Hit@1 1.0으로 임베딩(0.8)을 이겼고, 환각 억제에서도 더 안전했습니다. 코퍼스가 수천 개로 늘면 임베딩으로 전환할 준비가 되어 있습니다.

**Q. API 키가 프론트엔드 번들에 포함되면 보안 문제가 있지 않나요?**
A. 그 문제가 있었고, 1차 제출 전에 고쳤습니다. 지금은 프론트엔드가 LLM 을 직접 부르지 않고 `POST /api/llm` 서버리스 함수로 우회합니다. 키는 Vercel 환경변수에만 있고 빌드 산출물에는 들어가지 않습니다. 배포된 번들을 검색해도 키 문자열이 나오지 않습니다.

**Q. Qwen2.5-7B도 환각이 없었는데 왜 Groq를 선택했나요?**  
A. F3-03 환각 억제는 두 모델 모두 v1 RAG에서 성공했습니다. 그러나 Qwen은 URL 포함(4/5 vs 1~2/5)과 미검증 경고 문구 등 구체적인 프롬프트 지시를 이행하는 능력이 낮았습니다. 70억 파라미터 vs 700억 파라미터의 차이가 이 부분에서 드러납니다. 또한 로컬 Ollama는 추론 속도가 느리고 서버 인프라가 필요한데, Groq는 인프라 없이 동일 수준 이상의 성능을 무료로 제공합니다.
