# 화성시 AI 경영동행 서비스 — 테스트케이스 설계 가이드
### (매칭 알고리즘 담당자용)

이 문서는 LLM·RAG 벤치마크에 쓸 테스트케이스를 만들기 위한 템플릿입니다.
여기 있는 예시들과 같은 패턴으로 기능당 20~30개씩 만들어주시면 됩니다.

---

## 0. 왜 이렇게 만들어야 하나

- **일반 케이스만 만들면 안 됩니다.** 모델들이 실제로 자주 틀리는 지점(트랩)을 일부러 섞어야 모델 간 차이가 드러납니다.
- **정답(golden_answer)은 후보 답변 생성 단계에서 모델에게 노출되면 안 됩니다.** 별도 파일로 분리 보관하고, 채점 단계에서만 사용하세요.
- 케이스 하나하나가 "이 모델이 이걸 틀리면 실제 사용자가 어떤 피해를 입는가"를 상상할 수 있어야 합니다.

---

## 1. 공통 데이터 포맷

케이스는 아래 컬럼을 가진 CSV(또는 JSON)로 관리해주세요.

| 컬럼명 | 설명 | 예시 |
|---|---|---|
| `case_id` | 기능명-일련번호 | `F1-01`, `F2-05`, `F3-12` |
| `type` | `normal`(일반) 또는 `trap`(트랩) | `trap` |
| `trap_type` | 트랩인 경우 유형 태그 (아래 2절 참고) | `missing_info_omission` |
| `input_prompt` | 모델에게 실제로 줄 질문/입력 | (아래 예시 참고) |
| `context_docs` | 모델이 참고해야 할 근거 문서(공고문 등). RAG 케이스는 필수 | `HS_청년창업_2026.pdf` |
| `golden_answer` | 사람이 검증한 정답 (모델에게는 절대 노출 금지) | — |
| `judge_rubric_note` | 이 케이스를 채점할 때 특히 봐야 할 포인트 | "재산 구간 확인 질문 생략 여부" |
| `critical_failure_if` | 이걸 틀리면 무조건 "중요 실패"로 처리하는 조건 | "재산 정보 누락을 0원으로 단정" |

## 2. 트랩 유형 (기능 공통으로 재사용 가능)

지난 프로젝트(Policy Bridge)에서 실제로 모델들이 반복적으로 틀렸던 패턴입니다. 화성시 케이스에도 그대로 이식하세요.

| 트랩 유형 태그 | 의미 |
|---|---|
| `condition_ambiguity` | 조건 정의가 모호함 (예: "재산 기준"이 정확히 뭘 뜻하는지 공고문에 명시 안 됨) |
| `missing_info_omission` | 사용자가 언급 안 한 정보를 모델이 임의로 0/없음으로 단정 |
| `unmapped_category` | 표준 업종표에 없는 애매한 직종(프리랜서, 무자료 자영업 등) |
| `range_vs_single_value` | 범위로 답해야 하는데 모델이 단일 숫자로 확정해버림 |
| `mutually_exclusive_conflict` | 상호 배타적인 조건(청년/중장년 등)이 동시에 걸리는 경우 |
| `deadline_or_closed_case` | 이미 마감되었거나 접수 종료된 공고를 다루는 경우 |
| `multi_doc_conflict` | 근거 문서 두 개의 내용이 서로 다르거나 상충 |

## 3. 기능1 — 지원사업 매칭 조건 해석 (예시 5개)

**F1-01 (normal)**
- 입력: "화성시 향남읍에서 카페 창업 준비 중인 만 29세, 창업 경험 없음, 기초생활수급자입니다. 받을 수 있는 지원사업 알려주세요."
- 근거문서: `HS_청년창업지원_2026.pdf`
- 골든답안: 나이(29세 만족)·창업경력(무경험 만족)·소득구간(기초수급 만족) → 해당 공고 매칭, 조건 근거 3가지 명시
- 채점포인트: 왜 매칭됐는지 근거를 조건별로 나눠 설명하는지

**F1-02 (trap: missing_info_omission)**
- 입력: "화성시 동탄에서 소매업 하려는 예비창업자예요. 나이는 34세고, 재산 관련해서는 딱히 말 안 했어요."
- 골든답안: 재산 정보가 없으므로 **확정 매칭 금지**, "재산 구간을 알려주시면 더 정확히 안내드릴게요" 같은 확인 질문 필수
- `critical_failure_if`: 재산을 임의로 "일반" 또는 "0원"으로 가정하고 매칭 결과를 확정하는 경우

**F1-03 (trap: unmapped_category)**
- 입력: "저는 프리랜서 디자이너인데 이번에 화성시에 작업실 겸 스튜디오를 차려요. 소상공인 지원 대상 되나요?"
- 골든답안: 프리랜서를 기업 직급표/업종표에 억지로 매핑하지 않고, "사업자등록 여부"와 "매장형 사업장 요건" 등 실제 판단 기준을 되묻는 답변
- `critical_failure_if`: 프리랜서를 임의로 특정 표준 업종 코드에 강제로 끼워맞춤

**F1-04 (trap: condition_ambiguity)**
- 입력: "재산 기준이 정확히 뭘 말하는지 모르겠는데 그냥 저 신청 가능한지만 알려주세요."
- 골든답안: 재산 기준의 정의(부동산·금융자산 포함 여부 등)가 공고문에 명시 안 돼 있다면, 모델이 스스로 단정하지 말고 공고문에 나온 범위 그대로만 안내 + "정확한 기준은 담당 기관 확인 필요" 명시
- 채점포인트: 공고문에 없는 내용을 지어내지 않는지(환각 여부)

**F1-05 (trap: deadline_or_closed_case)**
- 입력: "화성형 청년 인테리어 지원사업 아직 신청 가능한가요?" (해당 공고는 이미 마감된 상태로 세팅)
- 골든답안: 마감 사실 명시 + "다음 회차 알림 신청" 안내로 자연스럽게 전환
- `critical_failure_if`: 마감된 공고를 신청 가능한 것처럼 안내

## 4. 기능2 — 세무 일정 안내 (예시 4개)

**F2-01 (normal)**
- 입력: "저 화성시에서 카페 하는데 부가세 신고 언제까지예요?"
- 골든답안: 일반과세자 기준 확정신고 기한(예: 1월 25일) 명시 + 간이과세자와 다를 수 있음을 안내
- 채점포인트: 과세유형에 따라 기한이 달라진다는 점을 놓치지 않는지

**F2-02 (trap: missing_info_omission)**
- 입력: "종합소득세 신고 언제까지죠?" (사업자 유형·과세 방식 언급 없음)
- 골든답안: 일반적 기한 안내와 함께, 정확한 안내를 위해 "간이과세자이신가요, 일반과세자이신가요?" 같은 확인 질문 포함
- `critical_failure_if`: 사업자 유형을 임의로 하나로 가정하고 단정적으로 답변

**F2-03 (trap: range_vs_single_value)**
- 입력: "가산세 얼마나 붙어요?"
- 골든답안: 가산세율은 지연 기간·사유에 따라 범위로 달라짐 → 범위와 조건을 함께 제시 (단일 숫자로 확정 금지)
- `critical_failure_if`: 조건 무시하고 단일 %만 딱 잘라 답변

**F2-04 (trap: condition_ambiguity)**
- 입력: "저 올해 처음 사업자 냈는데 첫 신고는 좀 다른가요?"
- 골든답안: 신규사업자 특례가 있다면 명시, 없다면 "일반 절차와 동일하다"를 명확히 하고 애매하게 얼버무리지 않음

## 5. 기능3 — 신청 동행 / 서류 체크리스트 (RAG, 예시 4개)

### 5-0. 이 기능만의 입력 구조 (중요)

기능1·2와 다르게, 기능3은 **매칭 엔진의 판정 결과가 RAG 입력의 일부로 그대로 들어갑니다.** 순수하게 사용자 질문만 던지는 게 아니라, 아래처럼 "매칭 엔진 출력 + 공고문 청크 검색"이 합쳐진 프롬프트를 모델에게 줍니다.

```
RAG 입력 = policy_id / notice_id
         + 사용자 조건 요약
         + 매칭 엔진 판정 (충족/조건부/확인필요로 이미 나뉜 상태)
         + 예상 서류(1차 추정치, 틀릴 수 있음)
              ↓ (여기에 공고문 원문 청크 검색 결과 결합)
출력 = 신청가능성 / 공통필수 서류 / 조건부필수 서류
     / 추가확인사항 / 발급안내 / 주의사항
```

즉 **모델이 처음부터 서류를 판단하는 게 아니라, 매칭 엔진이 1차로 판정해준 것을 공고문 원문과 대조해서 검증·보완하는 역할**입니다. 그래서 테스트케이스도 "매칭 엔진 판정이 이미 있고, 그게 맞는지 RAG가 원문으로 재확인/보완하는지"를 트랩으로 심어야 합니다.

### 5-1. 케이스 포맷 (기능1·2와 다른 추가 컬럼)

| 컬럼명 | 설명 |
|---|---|
| `matching_engine_output` | 매칭 엔진이 이미 판정한 결과 (충족/조건부/확인필요 + 예상서류) — 일부러 불완전하거나 살짝 틀리게 넣기도 함 |
| `qrels` | 정답 근거가 되는 문서 청크 ID와 관련도 점수. RAG 검색 품질(nDCG 등) 평가에도 재사용 |

---

**F3-01 (normal) — 부모님과 동거 중인 예비창업 청년**
- RAG 입력:
  - `notice_id`: HS-2026-014 (화성시 청년 예비창업 지원)
  - 사용자: 만 26세, 화성시 향남읍, 미혼, 부모님과 동거, 창업 경험 없음
  - 매칭 엔진 판정: 나이·지역·창업경력 충족 / 소득·자산 확인 필요
  - 예상 서류: 주민등록등본, 가족관계증명서, 금융정보 제공 동의서
- 골든답안:
  - 신청가능성: 추가 확인 필요
  - 공통필수: 주민등록등본, 개인정보 수집·이용 동의서
  - 조건부필수: 가족관계증명서(부모 동거 조건과 연결될 때만), 부모 소득·자산 확인 서류
  - 추가확인: 본인·부모 월평균 소득, 총자산
- `qrels`: Q_F3_01 → `HS-2026-014_document_common_01`(3), `HS-2026-014_family_condition_02`(3), `HS-2026-014_income_asset_01`(2)
- 채점포인트: 매칭 엔진이 "예상 서류"로 준 것을 그대로 베끼지 않고, 실제 공고 원문 근거(source_chunk_id)로 재검증했는지

**F3-02 (trap: matching_output_uncritical_copy) — 매칭 엔진 예상이 실제로 틀린 경우**
- RAG 입력:
  - `notice_id`: HS-2026-022 (화성시 소상공인 재기지원)
  - 매칭 엔진 판정(의도적으로 불완전하게 세팅): 예상 서류에 "사업자등록증"만 있음
  - 실제 공고 원문(청크)에는 "폐업사실증명원"도 공통 필수로 명시되어 있음
- 골든답안: 매칭 엔진이 놓친 "폐업사실증명원"을 원문 근거로 찾아내 추가
- `critical_failure_if`: 매칭 엔진이 준 서류 목록만 그대로 출력하고 원문 대조를 안 함 (이게 트랩의 핵심 — RAG가 매칭 엔진을 맹신하는지 검증)
- 채점포인트: 이게 바로 "RAG가 매칭 엔진 출력을 검증·보완하는 역할을 하는지" 확인하는 케이스

**F3-03 (trap: multi_doc_conflict)**
- 입력: "사업자등록증 사본이 꼭 필요한가요?"
- 근거문서: 두 문서 중 하나는 "필수", 하나는 "선택"으로 다르게 기재되어 있도록 의도적으로 세팅
- 골든답안: 상충 사실을 인지하고 "공고문마다 다르게 안내되어 있어 확인이 필요하다"고 명시 (하나만 보고 단정하지 않음)
- `critical_failure_if`: 상충을 무시하고 한쪽 문서만 근거로 확정 답변

**F3-04 (trap: missing_info_omission) — 예비부부/공동사업자처럼 조건부 서류가 있는 경우**
- 입력: "혼인관계증명서도 내야 하나요?" (공고문에 조건부로만 명시된 서류)
- 골든답안: "특정 조건(예: 부부 공동사업자인 경우)에만 필요"라는 조건부 사실을 누락 없이 전달
- `critical_failure_if`: 조건부 서류를 아예 언급 안 하거나, 무조건 필요/불필요로 단정

**F3-05 (trap: deadline_or_closed_case)**
- 입력: "서류 준비하는 데 보통 얼마나 걸려요? 마감이 언젠데요?"
- 골든답안: 예상 소요기간 + 마감일을 함께 제시해서 "지금 시작하면 늦을 수도 있다"는 판단을 사용자가 스스로 할 수 있게 함

## 6. 담당자 셀프 체크리스트 (케이스 추가로 만들 때)

- [ ] 기능당 최소 20개 이상 (일반 60~70% + 트랩 30~40% 비율 권장)
- [ ] 트랩 유형(2절)이 골고루 섞였는가 (한 유형에 몰리지 않게)
- [ ] `golden_answer`가 후보 답변 생성용 프롬프트/파일에 절대 섞이지 않았는가
- [ ] `critical_failure_if` 조건이 채점자가 봐도 애매하지 않고 명확한가
- [ ] 실제 화성시 지역명(동탄·향남·남양읍 등)과 실제 존재하는(또는 가상이지만 현실적인) 공고명을 썼는가
- [ ] RAG 케이스(기능3)는 반드시 `context_docs`에 실제 참고할 문서를 지정했는가
- [ ] 기능3 케이스는 `matching_engine_output`(매칭 엔진 판정)을 입력에 포함했는가 — 특히 일부 케이스는 **매칭 엔진 판정을 일부러 불완전/오류로 세팅**해서, RAG가 이를 맹신하지 않고 원문으로 검증하는지 테스트했는가
- [ ] 기능3 케이스에 `qrels`(정답 근거 청크 ID + 관련도 점수)를 남겼는가 — 이건 임베딩·RAG 검색 품질(nDCG 등) 평가에도 그대로 재사용됨
