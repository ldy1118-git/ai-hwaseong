# 매칭 엔진 출력 스키마 (제안)
### LLM+RAG 담당 → 매칭 알고리즘 담당자 전달용

---

## 안내

아래는 **제안 스펙**입니다. 이 형태로 만들어주시면 챗봇(신청동행·예외질문 응답) 쪽에서 바로 연동할 수 있어요.
다만 구현하시다가 특정 필드가 로직상 어렵거나 불필요하면 편하게 말씀해주세요 — 필드명·구조는 협의 가능합니다.

---

## 1. 전체 구조

```
매칭 엔진 출력
 ├─ notice_id / policy_id      → 어떤 공고인지 식별
 ├─ user_profile               → 사용자가 입력한 조건 (그대로 echo)
 ├─ condition_results[]        → 조건 하나하나에 대한 판정
 ├─ overall_status             → 종합 판정
 ├─ expected_documents[]       → 예상 서류 목록 (신뢰도 포함)
 └─ generated_at               → 판정 생성 시각
```

---

## 2. 필드별 설명

### 2-1. 식별 정보

| 필드명 | 타입 | 설명 |
|---|---|---|
| `notice_id` | string | 공고 고유 ID (예: `HS-2026-014`) |
| `policy_id` | string | 정책 유형 ID (예: `HS_YOUTH_STARTUP`) — 없으면 생략 가능 |

### 2-2. 사용자 조건 (echo)

| 필드명 | 타입 | 설명 |
|---|---|---|
| `user_profile` | object | 사용자가 입력한 조건을 그대로 담음 (나이, 지역, 경력, 업종, 재산구간 등) |

### 2-3. 조건별 판정 — **가장 중요한 부분**

| 필드명 | 타입 | 설명 |
|---|---|---|
| `condition_results` | array of object | 조건 하나당 객체 하나 |
| ㄴ `condition` | string | 조건명 (예: `age`, `region`, `career`, `category`, `income_asset`) |
| ㄴ `status` | string (enum) | `충족` / `불충족` / `확인필요` 3가지 중 하나로 고정 |
| ㄴ `detail` | string | 판정 이유 짧게 (예: "만 26세, 공고 기준 만 39세 이하 충족") |

> **왜 이 필드가 제일 중요한가**: `확인필요` 상태가 있어야, RAG/LLM이 "이 정보는 사용자에게 되물어야 한다"는 걸 알 수 있어요. 이게 없으면 모델이 정보 부족을 임의로 단정해버리는 문제(지난 벤치마크에서 반복됐던 실패 패턴)가 그대로 재현될 수 있습니다.

### 2-4. 종합 판정

| 필드명 | 타입 | 설명 |
|---|---|---|
| `overall_status` | string (enum) | `신청가능` / `조건부` / `확인필요` / `대상아님` 중 하나 |

### 2-5. 예상 서류 — **신뢰도 표시 필수**

| 필드명 | 타입 | 설명 |
|---|---|---|
| `expected_documents` | array of object | 서류 하나당 객체 하나 |
| ㄴ `name` | string | 서류명 (예: "가족관계증명서") |
| ㄴ `required_type` | string (enum) | `공통필수` / `조건부필수` / `해당시제출` |
| ㄴ `confidence` | string (enum) | `confirmed`(공고 원문에서 확정 확인) / `estimated`(엔진이 조건 기반으로 추정, 원문 대조 필요) |
| ㄴ `trigger_reason` | string | 조건부필수인 경우, 어떤 조건 때문에 필요한지 (예: "부모 동거 조건과 연결") |

> **왜 `confidence` 필드가 필요한가**: 이 값이 `estimated`면, RAG가 이걸 그대로 믿지 않고 공고 원문을 검색해서 검증하도록 설계할 수 있어요. `confirmed`면 검증을 생략하고 빠르게 답변 가능합니다. 이 구분이 없으면 RAG가 매번 전체를 재검증해야 해서 비효율적입니다.

### 2-6. 메타 정보

| 필드명 | 타입 | 설명 |
|---|---|---|
| `generated_at` | string (ISO8601) | 판정이 생성된 시각 |

## 3. 예시 JSON

```json
{
  "notice_id": "HS-2026-014",
  "policy_id": "HS_YOUTH_STARTUP",
  "user_profile": {
    "age": 26,
    "region": "화성시 향남읍",
    "marital_status": "미혼",
    "living_with_parents": true,
    "career_experience": "없음"
  },
  "condition_results": [
    { "condition": "age", "status": "충족", "detail": "만 26세, 공고 기준 만 39세 이하 충족" },
    { "condition": "region", "status": "충족", "detail": "화성시 거주 확인" },
    { "condition": "career", "status": "충족", "detail": "창업 경험 없음 조건 충족" },
    { "condition": "income_asset", "status": "확인필요", "detail": "소득·자산 정보 미입력" }
  ],
  "overall_status": "확인필요",
  "expected_documents": [
    {
      "name": "주민등록등본",
      "required_type": "공통필수",
      "confidence": "confirmed",
      "trigger_reason": null
    },
    {
      "name": "가족관계증명서",
      "required_type": "조건부필수",
      "confidence": "estimated",
      "trigger_reason": "부모 동거 조건과 연결될 때만 필요 — 원문 확인 필요"
    }
  ],
  "generated_at": "2026-08-10T09:00:00+09:00"
}
```

## 4. 요청 시 함께 전달할 말

> "이 포맷대로 부탁해요. 근데 구현하다가 특정 필드가 로직 구조상 안 나오거나 번거로우면 편하게 말씀해주세요 — 필드명·구조는 같이 조정하면 돼요. 급한 건 아니고 다음 주 초까지만 주셔도 충분해요."
