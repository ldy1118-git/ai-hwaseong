# Git 협업 규칙

3인 팀, 마감 8/20. **가볍게 가되 사고만 막는다**가 원칙이다.
담당 폴더가 서로 겹치지 않아서 충돌이 날 일이 원래 적다.

---

## 브랜치 구조

```
main                    항상 동작하는 상태. 여기가 깨지면 다 같이 멈춘다
├── feat/matching       성현   — matching/
├── feat/llm            서희   — llm/, 통합 UI
└── feat/policy         대윤   — policy_data/
```

개인 브랜치는 **길게 유지**한다. 기능마다 새로 파지 않는다.
마감이 짧아서 브랜치를 늘리면 관리 비용만 커진다.

---

## 규칙 5개

1. **`main`에 직접 푸시하지 않는다.** 통합 시점(8/15, 8/18)에만 머지한다.
2. **`git push --force` 절대 금지.** 남의 커밋이 사라진다. 되돌릴 방법이 없다.
3. **자기 담당 폴더만 수정한다.** 남의 폴더를 고쳐야 하면 먼저 디코에 말한다.
4. **작업 시작 전에 `main`을 받아온다.** 하루 한 번이면 충분하다.
5. **커밋 메시지는 한글로 무엇을 왜.** `수정`, `ㅇㅇ` 같은 건 나중에 발표 자료 만들 때 본인이 고생한다.

## 매일 쓰는 명령

### 처음 한 번 (각자 로컬에서)

```bash
git clone https://github.com/ldy1118-git/ai-hwaseong.git
cd ai-hwaseong
git checkout -b feat/matching        # 본인 브랜치 이름으로
git push -u origin feat/matching
```

### 작업 시작할 때

```bash
git checkout feat/matching
git pull origin main                 # main의 최신 변경을 내 브랜치로
```

### 작업 저장할 때 (자주)

```bash
git add .
git commit -m "OCR 업태 오인식 후처리 추가"
git push
```

### 내 모듈이 완성돼서 main에 올릴 때

```bash
git checkout main
git pull
git merge feat/matching
git push
git checkout feat/matching           # 다시 내 브랜치로 돌아오기
```

GitHub에서 Pull Request를 만들어 머지해도 된다. 리뷰를 기다릴 시간은 없으니
**본인이 만들고 본인이 머지**하면 된다. 대신 무엇을 바꿨는지 기록이 남아서
나중에 발표 자료 만들 때 편하다.

## 충돌이 날 수 있는 곳 두 군데

담당 폴더가 갈려 있어서 대부분은 안 부딪힌다. 딱 두 군데만 조심하면 된다.

### 1. 화면(index.html)

`matching/index.html`은 **성현의 테스트용 페이지**다. 그대로 둔다.
실제 서비스 UI는 서희가 별도 폴더에서 새로 만든다.
같은 파일을 둘이 고치는 상황을 아예 만들지 않는 게 목적이다.

### 2. 공고 JSON

| 위치 | 용도 | 주인 |
|---|---|---|
| `matching/notices/` | 성현이 손으로 만든 샘플 19건. 매칭 로직 테스트용 고정 데이터 | 성현 |
| `policy_data/notices/` | 대윤이 크롤링/API로 모은 실제 공고 | 대윤 |

두 폴더를 분리해서 쓴다. 같은 폴더에 양쪽이 파일을 쏟아부으면 섞인다.

`matching.py`는 공고 폴더를 인자로 받으므로 통합 시점에 바꾸기만 하면 된다.

```bash
python3 matching.py --notices ../policy_data/notices
```

## 모듈 사이 규격

모듈은 **JSON 파일**로 주고받는다. 매칭 엔진의 출력이 LLM의 입력이 된다.

```
사용자 입력 ─┐
             ├─→ matching ─→ JSON ─→ llm ─→ 화면
사업자등록증 ─┘                ↑
                        policy_data
```

이 JSON 형식은 **서희가 정의해서 성현에게 전달**한다.
노션 「매칭알고리즘」 페이지에 스키마가 정의돼 있고, matching.py가 이미 이를 구현했다.
형식을 바꿔야 하면 반드시 디코에 먼저 공유한다. 말없이 바꾸면
상대방 코드가 조용히 깨지고, 원인 찾는 데 몇 시간 날아간다.

규격 원본은 노션 「매칭알고리즘 — 매칭 엔진 출력 스키마」 페이지다.
저장소에 따로 복사본을 두지 않는다. 두 곳에 있으면 반드시 어긋난다.

## 사고 났을 때

**커밋을 잘못했다 (아직 푸시 전)**
```bash
git reset --soft HEAD~1     # 커밋만 취소, 작업 내용은 남음
```

**남의 작업을 덮어쓴 것 같다**
```bash
git reflog                  # 최근 이동 기록 전부 나옴
git reset --hard <해시>      # 그 시점으로 복구
```

**충돌이 났다**

당황하지 말고 파일을 연다. `<<<<<<<`와 `>>>>>>>` 사이에 양쪽 내용이 다 있다.
남길 것만 두고 표시줄을 지운 뒤 `git add` → `git commit`.
판단이 안 서면 상대방에게 물어본다. 혼자 지우지 않는다.

**정말 모르겠다**

`git push --force`만 하지 않으면 거의 다 복구된다. 단톡방에 물어보기.

## 올리면 안 되는 것

`.gitignore`가 막아주지만 한 번 더 확인한다.

- **사업자등록증 이미지, `users/` 폴더** — 실명·사업자번호·생년월일·주소가 들어있다
- `.venv/` (1.4GB)
- 모델 가중치 `*.pth`, `*.bin`
- API 키, 토큰이 든 파일

푸시 전에 `git status`로 무엇이 올라가는지 눈으로 본다.
