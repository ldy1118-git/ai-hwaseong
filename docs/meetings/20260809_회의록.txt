3. 서비스 전체 흐름 (확정)
================================================================================

3-1. 최초 진입
--------------------------------------------------------------------------------
첫 화면 = 플랫폼 소개 + 버튼 3개. 버튼에 마우스를 올리면 요약 설명 표시. (19:36)

  [1단계 분기]  예비 사업자(창업 전)  /  사업자(창업 후)     (20:38)

3-2. 창업 전 — 3단계 분기  (18:16)
--------------------------------------------------------------------------------
  (1) 하나도 계획이 없어요
  (2) 대략적인 계획은 있어요
  (3) 구체적인 계획이 있는데 비교하고 싶어요

  · 분기를 나누는 이유: 정보를 "먼저 제공하고 입력받느냐" vs "바로 입력받느냐"의
    차이. 입력 항목 자체는 동일하되 안내 방식이 달라짐. (22:03)

  · (1) 계획 없음 → 상권분석을 붙이지 않고, LLM 문답으로 업종을 유도.
    예: "앉아서 일하고 싶은지 / 무거운 것을 들 수 있는지 / 불이 무서운지"
    → 성향에 맞는 업종 추천 → 결과적으로 (2)번 흐름으로 합류. (1:32:59)
    ※ 계획 없는 사용자에게 상권분석까지 제공하는 것은 데이터 요구량 대비
      비용이 커서 MVP 범위에서 제외. (1:31:51)

  · (2)(3) → 조건 입력 → 정책 매칭 → 상위 3건 추천 → 신청 절차 안내

3-3. 창업 후 (사업자)
--------------------------------------------------------------------------------
  사업자등록증 사진 업로드 → OCR로 정보 자동 추출 → 부족한 정보만 추가 입력
  → 동일하게 매칭. (1:39:38)
  · 사업자등록증에는 이름/생년월일/개업일/소재지/업종이 담김. 거래처에도
    통상 전달하는 문서라 민감도는 낮다고 판단, 일단 수집하기로.
    등록번호 활용 여부는 보류. (1:40:31)

3-4. 매칭 이후 (핵심 차별점)
--------------------------------------------------------------------------------
  매칭 → 필요 서류 안내 → 발급 방법 안내 → 신청 완료까지 동행. (1:22:23)
  · 신청 후 결과 발표일을 DB에 저장 → 발표 시점에 알림 발송. (1:37:50)
  · 로그인은 선택. 매칭 결과를 먼저 보여주고 유의미하다고 느낀 시점에
    회원가입 유도(알림 수신용). (1:36:50)


================================================================================
4. 입력받을 항목 (지원사업 매칭 기준)
================================================================================

  1) 나이            ← 가장 중요한 선정 기준
  2) 재산 / 소득분위
  3) 창업 경험 유무 (신규 창업 여부 — 국가 지원은 신규에 집중되는 경우 다수)
  4) 업종
  5) 위치            ← 화성시 내로 한정되므로 변별력은 낮음
  6) 지원받고 싶은 분야(카테고리)  예) 부동산·임대, 전자기기, 유류비 등
  + 예산 (선택)
                                                        (38:03~39:53, 58:21)

- 모든 항목에 "모르겠어요" 선택지를 제공하여 진입 장벽을 낮춤. (1:26:07)
- 소득분위를 모르는 경우: LLM으로 추정 계산 제공.
  (가족 구성원 직업·소득을 자연어로 입력 → 통계청 기준으로 추정.
   이전 청년 주거정책 프로젝트에서 사용한 방식) (1:26:52)
- 재산 기준은 지원사업마다 정의가 달라 별도 확인 필요 → 미결 사항. (41:07)


================================================================================
5. 업종 데이터 처리
================================================================================

- 사업자등록증은 "업태(대분류) - 종목(세부)" 구조. 예: 업태=소매업,
  종목=무인문구·과자·음료 소매업 / 전자상거래 소매업. (07:47)
- 국세청 업종코드 자료를 일괄로 받아 DB(CSV)에 넣고 사용. 하드코딩 방식이
  가장 현실적이라고 판단. (25:12, 25:42)
- 사용자가 업종 분류를 어려워하므로, 카테고리별 예시를 함께 노출. (26:06)

온라인 사업 관련 정리 (08:21~15:09)
- 온라인 서비스도 사업자등록에 주소가 반드시 필요 → 소재지 기준으로
  해당 지자체 정책 적용 대상이 됨. 따라서 온라인 업종도 서비스 범위에 포함.
- 오프라인 소매업과 별개로 "전자상거래 소매업" 업종을 추가 등록해야 온라인
  판매가 가능. 최초 등록 시에는 신규로 잡히고, 이후 업종 추가는 "추가"로 잡힘.
- 세금·혜택은 관할 세무서(소재지 기준)를 따르며 지자체마다 조례가 달라
  지원 비율이 상이(예: 파주 50% / 고양 25%). 단 화성시 내로 한정하면
  이 차이는 사실상 없음.

6. 주요 쟁점과 결론
================================================================================

[쟁점 1] 사업계획서를 매칭 단계에서 받아야 하는가?
--------------------------------------------------------------------------------
  · 성현: 대부분의 지원사업은 사업계획서가 사실상 필수이고, 심사도 여기서
    갈린다. (44:00)
  · 반론: 우리가 사업계획서를 일일이 확인해 매칭할 수는 없다. 사업계획서가
    필요한 시점은 "매칭 이후 신청 단계"다. (45:48)
  → [결론] 매칭 단계에서는 받지 않는다. 매칭 후 신청 절차 안내에서 등장시키고,
    MVP에서는 사업계획서의 큰 구조·양식 정도만 제시한다. 카테고리별로 요구
    서류가 비슷하므로 양식 템플릿화가 가능. (1:19:17)

[쟁점 2] 지원사업 자체가 적어서 매칭 결과가 안 뜨면?
--------------------------------------------------------------------------------
  · 성현: 소상공인/창업 분야 지원사업은 개수가 적고, 공고 기간이 짧으며
    (모집 1주일 수준), 매년 반복 여부도 불확실. 실제 타임라인은 1월 공고 →
    2~5월 모집 → 심사 → 11~12월 또는 익년 초 지급. (1:11:52)
  → [결론] 1차 예선에서는 "현재 해당 공고 없음 + 생기면 알림 발송"으로 처리.
    지난 공고를 예시로 보여주며 정보를 미리 입력받아 두고, 유사 공고가 뜨면
    알림/메일로 이어서 작성할 수 있게 함. 2차에서 추가 고민. (1:00:35, 1:20:49)

[쟁점 3] 서비스의 차별점은 무엇인가?
--------------------------------------------------------------------------------
  · 정보를 안내하는 서비스는 이미 많다. 없는 것은 "신청까지 데려가는" 서비스.
  · 더 근본적인 장벽은 행정 용어 자체. 임차인·주민등록표 등은 경험이 없으면
    모르는 단어이며, 이를 쉽게 풀어주는 것이 이전 프로젝트의 메인이었음.
    (1:23:47)
  → [결론] 어려운 용어에 마우스를 올리면 설명이 뜨는 방식(툴팁)으로 구현.
    용어 DB를 구축하되, DB에 없으면 LLM으로 짧게 생성하고 그 결과를 DB에
    자동 추가하는 구조. 초기 MVP는 자주 나오는 용어 위주로 구성 후 확장.
    (1:24:38, 1:35:17)

[쟁점 4] 상권분석의 위치
--------------------------------------------------------------------------------
  · 상권분석(매출)과 지원금은 결이 다름. 상권분석은 유동인구·주변 업종
    매출을 봐서 내 매출을 예측하는 것이고, 지원금은 내 조건에 따라 남이
    주는 돈. (1:28:33)
  → [결론] 매출 예측(예: "여기서 하면 2천만 원 나옵니다")은 하지 않는다.
    "이 동네 유동인구가 얼마고 주변 학교가 몇 개다, 손님이 될 만한 사람이
    많다/적다" 수준까지만 제공. 계획이 있는 사용자 흐름에 배치. (1:34:31)

[참고] 주제 변경 논의
--------------------------------------------------------------------------------
  지원사업 수가 적다는 이유로 주제 변경(복지 분야 등) 가능성이 언급되었으나,
  주제는 변경하지 않고 소상공인/창업으로 진행하기로 정리.
  선정 이유는 "가장 절차가 복잡하고 이탈률이 높은 영역"과 같은 논리로
  구성 가능. (35:17, 36:05)

8. 기술 결정
================================================================================

서비스 형태 (1:15:15)
  · 웹으로 먼저 제작 → 이후 앱에 웹뷰로 탑재.
  · 이유: 공동인증서/카카오 로그인 등 실제 신청 절차가 모바일 단독으로는
    어려움. 웹을 만들어 두면 앱에 얹는 것은 어렵지 않음.

배포 (1:43:13 ~ 1:52:16)
  · 성현이 개인 서버(윈도우)와 도메인을 보유 → Cloudflare/Vercel 등을 거치지
    않고 자체 서버에서 직접 배포 가능. Supabase 등 DB 연동도 확인됨.
  · 장점: Git push 없이도 서버에서 직접 개발·구동 가능, 자유도가 높음.
  · Git은 코드 저장·제출용으로 계속 사용 (심사위원/교수 열람).
  · 배포는 서비스 완성 후에 결정. 여의치 않으면 실제 매칭이 아닌
    "흐름만 보여주는 체험판" 형태로 배포해도 무방.

LLM (2:00:29 ~ 2:03:42)
  · 파인튜닝은 하지 않음.
  · 임베딩 모델 / LLM 모델을 각각 10개 정도 놓고 비교 테스트 → 보고서 형태로
    정확도 평가. 용량이 커서 하루 종일 걸릴 수 있음.
  · RAG 적용 전 / 후 결과 차이를 발표 자료에 포함.
  · 이전 프로젝트에서 이 부분을 메인으로 담당했던 사람에게 자문 예정.

프론트엔드 (2:16:28 ~ 2:20:30)
  · Streamlit 검토 중. 이전 프로젝트에서 HTML로 작업한 화면을 백엔드와
    연동하는 과정에서 깨지는 부분이 많아 최종적으로 Streamlit으로 전환한 경험.
  · 진행 상황/체크리스트 표시에는 Streamlit이 적합하다는 판단.
  · React + TypeScript도 후보. 최종 결정은 보류.
  · 각자 테스트용으로는 형태 무관하게 만들고, 통합 시 작성자가 손보기로.
