## 1. 시스템 구성

```
        [ 사용자 브라우저 ]
                │
                │  React 18 + Vite 6 + Tailwind (project/)
                ▼
        [ Vercel ]  ── 정적 프론트 + 파이썬 서버리스 함수
                │
    ┌───────────┼───────────────┬──────────────┐
    ▼           ▼               ▼              ▼
 /api/match  /api/llm       /api/terms    /api/auth/kakao
 매칭 엔진   LLM 대리호출    용어 사전      카카오 로그인
    │           │                             │
    │           ▼                             ▼
    │      Groq / Gemini                 Supabase (PostgREST)
    ▼
 policy_data/notices/*.json  (공고 59건, 배포에 같이 실린다)
                ▲
                │  매일 06:00 KST
        [ GitHub Actions ] ── 기업마당 API → 추출 → 검사 → 자동 커밋
```

### 왜 이런 모양인가

| 결정 | 이유 |
|---|---|
| **파이썬 API에 외부 패키지 0개** | Vercel 함수 용량 제한. `urllib`·`hmac`·`json`만 쓴다. `requirements.txt`가 아예 없다. PyJWT 대신 `hmac`으로 JWT를 직접 만들고, psycopg 대신 Supabase의 PostgREST를 HTTP로 부른다. |
| **LLM을 프론트에서 직접 안 부른다** | Vite의 `VITE_` 환경변수는 **번들에 평문으로 박힌다.** 실제로 테스트 키를 넣고 빌드했더니 번들 JS에 3번 나왔다. 그래서 `POST /api/llm`으로 우회하고 키는 Vercel 환경변수에만 둔다. |
| **공고를 DB가 아니라 JSON 파일로** | 공고는 하루 한 번 바뀌는 읽기 전용 데이터다. 배포에 같이 실으면 DB 왕복이 없어서 콜드스타트 뒤 첫 응답이 빠르고, 장애 지점이 하나 줄어든다. 갱신은 Git 커밋이 곧 배포다. |
| **Supabase는 사용자 데이터만** | 프로필·온보딩 답변만 저장한다. `service_role` 키는 RLS를 통과하므로 **서버에서만** 쓰고 `VITE_` 이름을 절대 붙이지 않는다. |

## 2. 데이터 파이프라인 — 공고는 어떻게 들어오는가

`./scripts/update_notices.sh` 한 줄이 다섯 단계를 돈다.

```
1/5  collect.py    기업마당 공공 API → 원본 1,551건
2/5  fetch_docs.py 첨부 공고문(PDF/HWPX) 다운로드 → pdftotext 로 텍스트
3/5  extract.py    자격요건·서류·기간·접수처 추출 → notices/*.json
4/5  validate.py   59건 스키마·매칭엔진 통과 검사
5/5  guard.py      "데이터가 줄지 않았는가" 검사
```

### 1단계 — 수집 (`collect.py`)

- 출처: **기업마당(bizinfo.go.kr) 지원사업 공고 API**, 인증키 방식.

#### 1,551 → 59 깔때기 (2026-08-20 실측)

| 단계 | 남는 수 | 떨어지는 수 | 무엇이 떨어지나 |
|---|---:|---:|---|
| 기업마당 전체 공고 | **1,551** | — | |
| ① 소상공인 신호 | **280** | 1,271 | 중견기업 R&D, 수출바우처, 벤처투자 등 소상공인과 무관한 사업 |
| ② 화성시민이 신청 가능 | **63** | **217** | **다른 시·도 전용 194건 + 경기도 내 다른 시·군 전용 23건** |
| ③ 이미 마감된 것 제외 | **63** | **0** | 오늘 기준 마감된 게 없었다 (59건 열림 + 4건 기간 미상 → **미상은 남긴다**) |
| ④ 소상공인 대상 아님 명시 | **59** | 4 | 공고가 스스로 대상이 아니라고 적은 것 (아래 표) |

> **덩어리가 빠지는 곳은 ② 지역이다.** 소상공인 사업 280건 중 **217건이 다른 지역 전용**이다.
> 경북 34, 서울 19, 강원 19, 경남 14, 인천 13, 대전 13… 그리고 경기도 안에서도
> 시흥 7, 양주 2, 포천 2, 안양 2… 화성시민은 이걸 신청할 수 없다.
> **남는 63건 = 전국 사업 53 + 경기도 전체 사업 6 + 화성시 직접 사업 4.**

두 필터의 실제 코드는 이렇다.

```python
SOSANG = re.compile(r"소상공인|자영업|점포|소공인|골목|상점가")   # ①
USABLE = {"전국", "화성", "경기전체"}                            # ②
```

`scope()` 는 제목의 대괄호 표기 → 제목 속 시·군 이름 → 소관기관 순으로 보고
`화성 / 경기전체 / 전국 / 타시도(◯◯) / 경기-타지역(◯◯시)` 로 분류한다.

*①의 280건은 **날마다 바뀐다.** 공고가 매일 새로 뜨고 닫히기 때문이다.
며칠 전 실행에서는 272건이었다. 발표에서는 "1,551건 중 소상공인 사업 약 280건" 처럼
어림수로 말하거나, 그날 아침 값을 다시 확인하고 말할 것.*

#### 63건 → 59건, 왜 4건을 뺐나

거른 게 아니라 **소상공인이 신청할 수 없다고 공고가 스스로 말하는 것**만 뺐다.
규칙은 `extract.py` 의 `skip_reason()` 두 줄이 전부다.

| 뺀 공고 | 이유 |
|---|---|
| 2026년 3차 마케팅 구매상담회 참여기업 모집 공고 | 공고문에 **「소기업(소상공인)은 지원 제외」** 가 명시돼 있다 |
| [경기] 화성시 2026년 하반기 **여성 농업인** 특수건강검진 지원사업 | 소상공인이 아니라 농업인 대상 |
| 2026년 **농업용 면세유** 유가연동보조금 지원사업 공고 | 소상공인이 아니라 농업인 대상 |
| 2026년 지역·산업 맞춤형 인력양성사업 무료교육 **참여자·참여기업** 모집 | 소상공인이 아니라 **재직자** 대상 |

**「소상공인 제외」 공고가 왜 여기까지 왔나** — 필터 ①이 제목·요약·지원대상에서
`소상공인` 이라는 낱말을 찾는데, 이 공고는 **「소기업(소상공인)은 지원 제외」라는
제외 규정 안에 그 낱말이 들어 있어서** 통과했다. 낱말은 있는데 뜻은 정반대인 경우다.
그래서 공고문 본문까지 읽는 ④단계에서 다시 잡는다. **①이 넓고 ④가 정확한 구조다.**

**규칙 1 — 소상공인 지원 제외 (`EXCLUDES_SOSANG`)**

```python
r"소기업\s*[(（]\s*소상공인\s*[)）][^\n]{0,10}(?:은|는)?\s*지원\s*제외"
```

공고문 본문(앞 6,000자) + 요약 + 지원대상을 함께 본다.
**일부러 좁게 잡았다.** 그냥 "소상공인 제외"로 잡으면
「재해로 휴업 중인 소상공인 제외」 같은 **제외 규정의 예외 문장**까지 걸려서
정작 소상공인 대상 공고가 통째로 빠진다. 실제 공고문이 쓰는 표현은
「중소기업확인서 내 '소기업(소상공인)'은 지원 제외」 하나로 정형화돼 있어서 그것만 잡는다.

**규칙 2 — 대상 자체가 다른 사람 (`NOT_SOSANG`)**

```python
r"여성\s*농업인|농업경영체|농업인|재직자|영농|어업인"
```

이쪽은 **제목과 요약만** 본다. 본문까지 보면 「지원 제외: 농업인」 같은 한 줄에 걸려서
멀쩡한 소상공인 공고가 빠진다. 업종이 아니라 **신분이 아예 다른** 사업만 걸러낸다.

> **판단 기준은 「모르면 남긴다」이다.**
> 애매한 것은 빼지 않고 「확인필요」로 남긴다. 이 4건은 애매한 게 아니라
> 공고문이 대놓고 대상이 아니라고 적은 것들이다.
> 실제로 반대로 하다가 사고가 났었다 — 접수기간을 못 읽었다는 이유로
> 30건을 잘라내고 있었다(바로 아래).

*단, 「지역·산업 맞춤형 인력양성사업」은 재직자 교육이라 뺐지만
소상공인 사업주가 참여할 여지가 아주 없지는 않다. 경계에 있는 한 건이다.*

**여기서 잡은 버그 두 개 (질문 나오면 좋은 소재)**

1. **접수기간이 날짜가 아니라 문구인 공고 30건을 통째로 흘리고 있었다.**
   `is_open()` 이 날짜 두 개를 못 찾으면 `None`(모른다)을 돌려주는데, 추출 쪽이 그 `None`을
   falsy로 흘려서 **"모른다"를 "닫혔다"로 취급**했다.
   "예산 소진시까지", "상시 접수", "모집 완료시" 는 **지금 열려 있다는 뜻**이다.
   빠진 것들이 하필 희망리턴패키지(폐업·재기), 소상공인 고용보험료, 영세개인사업자
   체납액 징수특례 — 소상공인에게 제일 급한 것들이었다.
   → `is_open(r) is not False` 로 고쳐서 **29건 → 59건**.
2. **지역 필터 누수.** 「2026년 과천시 중소기업 및 소상공인 육성자금」이 대괄호 표기도 없고
   소관기관이 "경기도"로만 적혀 있어 전국 공고로 새어 들어왔다. 화성시민은 신청할 수 없다.
   → 제목에서 경기도 30개 시·군 이름을 찾아 걸러낸다.

### 2단계 — 첨부 공고문 (`fetch_docs.py`)

- 첨부파일을 받아 `pdftotext`로 텍스트를 뽑는다. **HWP(구형)와 이미지 PDF는 못 읽는다.**
- 59건 중 **공고문 확보 29건 / 요약만 30건**. 실패 사유는 로그에 형식별로 남는다
  (`hwp(처리 못 함)`, `이미지:0자`, `pdf:0자`).
- CI에 `poppler-utils`가 없으면 첨부를 하나도 못 읽는데 **파이프라인은 "성공"으로 끝난다.**
  실제로 2026-08-17에 그렇게 데이터가 깎였다. 그래서 지금은 `pdftotext`가 없으면
  스크립트가 **즉시 멈추도록** 막아뒀다.

#### 판독률 숫자 — 발표에서 뭐라고 말할지

| 세는 방법 | 값 | 쓸 것인가 |
|---|---|---|
| **배포된 59건 중 첨부 공고문 텍스트를 확보한 것** | **29건 = 49%** | ✅ **이걸 말한다** |
| 다운로드 시도 59건 중 텍스트가 나온 파일 수 | 31개 = 53% | ❌ 이 중 2개는 나중에 제외된 공고 것이다 |
| 요약이 200자 넘는 공고 (guard 기준) | 51건 = 86% | 내부 검사용 지표. 발표에 쓰지 말 것 |

**덱에 「53%」로 적혀 있으면 「49%」로 고칠 것.** 커밋 기록에도 41% → 49%로 남아 있다.

#### 이 숫자로 무슨 말을 하려는 건가

이건 **약점 고백이 아니라 문제 정의**다. 세 가지를 동시에 한다.

**① 이 문제가 왜 아직 아무도 안 풀었는지를 보여준다.**
공공데이터로 "공개"돼 있다는 말과 "기계가 읽을 수 있다"는 말은 다르다.
제목·마감일·소관기관 같은 **메타데이터는 API로 깔끔하게 온다.**
그런데 정작 사장님이 알아야 하는 것 — **누가 신청할 수 있는지, 무슨 서류가 필요한지** —
는 전부 **첨부파일 안**에 있다. 그 첨부가 구형 HWP(관공서 전용 포맷)이거나 스캔 이미지다.
**공개는 됐는데 읽을 수가 없다.** 그래서 지금까지 이걸 자동으로 한 서비스가 없었다.

**② 「확인필요」라는 설계가 왜 필요한지를 설명한다.**
절반을 못 읽으면 선택지는 둘뿐인 것처럼 보인다 —
못 읽은 건 전부 「신청가능」으로 두거나(헛걸음시킨다), 전부 빼거나(공고를 아예 못 본다).
**둘 다 사장님을 다치게 한다.** 그래서 세 번째 상태를 만들었다.
이 슬라이드가 없으면 「확인필요」가 왜 있는지 설명이 안 된다. **한 세트로 말할 것.**

**③ 화성시가 고칠 수 있는 문제를 짚는다.**
이건 우리가 코드로 못 고친다. OCR을 붙여도 스캔 품질에 좌우되고 정확도를 보장할 수 없다.
**그런데 공고를 낼 때 HWP 대신 텍스트가 살아 있는 PDF나 HTML로 내면 판독률이 바로 올라간다.**
해커톤 심사위원이 시청이라면, 이건 변명이 아니라 **구체적인 제안**이다.
"이걸 해주시면 저희 정확도가 이만큼 올라갑니다."

> **톤 주의.** 방어적으로 말하면 변명이 되고, 담담하게 말하면 신뢰가 된다.
> "못 했습니다"가 아니라 **"못 읽는 구간이 어디인지 저희가 정확히 알고 있고, 그걸 화면에 표시합니다"**.

**반박 대비 —** "그럼 나머지 30건은 아무것도 모르는 건가요?"
> 아닙니다. API 요약으로 사업 목적과 지원대상은 잡힙니다(59건 중 51건이 요약 200자 이상).
> 못 읽는 건 **상세 자격요건과 서류 목록**이고, 그 부분만 「확인필요」로 표시합니다.
> 공고 전체를 포기하는 게 아니라 **모르는 항목만** 모른다고 말합니다.

### 3단계 — 추출 (`extract.py`)

공고문 텍스트(없으면 요약)에서 규칙 기반으로 뽑는다. **LLM을 쓰지 않는다.**

| 뽑는 것 | 결과 |
|---|---|
| 자격조건 | **65개** (`business_status` 23, `requirements_unknown` 19, `requirements_open` 12, `categories` 3, `regions` 3, `min_business_months` 3, 매출 상·하한 각 1) |

## 3. 매칭 엔진 (`backend/matching.py`, 1,448줄)

프로필 하나가 들어오면 공고 59건 **전부**에 대해 판정을 만들어 돌려준다.
화면에서 「신청가능」만 세면 그게 "N건"이다.

### 3-1. 두 종류의 조건

| 종류 | 출처 | 예 |
|---|---|---|
| **자격 조건** (`eligibility`) | 공고문에 **적혀 있는** 것 | 「사업 상태 = 운영중」, 「업종 = 음식점」, 「연 매출 3억 이하」 |
| **적합도 조건** (`fit_conditions`) | 제목·지원대상에서 **추정한** 것 | 「화성시가 직접 하는 사업입니다」, 「청년 대상 사업입니다」 |

자격 조건은 틀리면 안 되니까 원문에 있을 때만 만들고,
적합도 조건은 **순위를 가르기 위해** 항상 만든다.

### 3-2. 판정은 세 값뿐

| 판정 | 점수 | 뜻 |
|---|---|---|
| 충족 | 1.0 | 확실히 맞는다 |
| **확인필요** | **0.5** | 근거가 없다 |
| 불충족 | 0.0 | 확실히 아니다 |

**전체 판정**은 이렇게 접는다.

```
하나라도 불충족 → 대상아님   (목록에서 빠진다)
하나라도 확인필요 → 확인필요
조건부/해당시제출 서류가 있으면 → 조건부
그 외 → 신청가능
```

> **왜 「확인필요」를 따로 두는가.**
> 이게 이 서비스의 핵심 설계다. 근거 없이 「대상아님」으로 자르면 사장님이 그 공고를
> **아예 못 본다.** 반대로 근거 없이 「신청가능」으로 주면 헛걸음을 시킨다.
> 그래서 모르는 것은 모른다고 화면에 적는다. 공고 매칭·세무일정·서류가 전부 같은 원칙이다.

### 3-3. 점수는 가중 평균

```
match_score = Σ(가중치 × 값) / Σ(가중치) × 100
```

| 조건 | 가중치 | 비고 |
|---|---|---|
| 지역 | 3.0 | 화성시 사업 1.0 · 경기도 사업 0.85 · 전국 사업 0.6 |
| 업종 | 3.0 | 업종 명시 사업 1.0 · 업종 무관 0.7 · 제조업 위주 0.35 |
| 사업 목적 | 3.0 / 2.0 | 폐업·창업 대상 여부 |
| 나이 | 2.5 | 청년·중장년 사업 |
| 지원 대상 | 1.5 ~ 3.0 | 소상공인 0.85 · 중소기업 확인필요 |

**단순 평균을 쓰면 안 되는 이유:** 「소상공인이면 누구나」 조건 하나만 걸린 공고가 전부
100점이 되어 59건 중 35건이 동점으로 뭉쳤다. 그래서 "자격은 되지만 **나를 위한 건 아닌**"
개방 조건은 값을 **0.7**만 준다(`OPEN_VALUE`).

### 3-4. 화면 정렬

**점수순이 아니다.** 마감이 급한 것(7일 이내)을 먼저 올리고 그다음이 적합도다.
그래서 홈의 남색 카드 「가장 잘 맞는 것」이 1위 점수와 다를 수 있다.
**발표에서 "1위가 몇 점"이라고 말하지 말 것.**

### 3-5. 실측 결과 (배포 서버에서 방금 확인)

| 프로필 | 신청가능 | 확인필요 | 대상아님 |
|---|---|---|---|
| 화성시 · 카페 · 예비창업 · 30세 | **10건** | 16건 | 33건 |
| 화성시 · 음식점 · 운영중 2년 · 45세 | **30건** | 18건 | 11건 |

같은 서비스, 같은 59건인데 사람이 바뀌면 10 → 30이 된다. **이게 시연의 핵심 장면이다.**

### 3-6. 데이터로 못 잡는 것은 override 로 잡는다

공고문에 "운영 중인 사업자"라고 적혀 있는데 문장 구조 때문에 규칙이 못 읽는 경우가 있다.
「음식점 미세먼지·악취 방지시설 설치 지원」이 예비창업자에게도 떴다.
**추출 로직을 손대면 재수집 때 다시 깎이므로**, `policy_data/eligibility_overrides.json`에
공고 ID별로 조건을 적어두고 로드 시점에 병합한다. 현재 2건 등록.

## 4. 행정용어 사전 + RAG 챗봇

### 4-1. 사전 (`policy_data/terms.json`)

**행정용어 31개 + 서류 26종 = 57항목.** 손으로 만들었고, 항목마다
`easy`(한 줄) · `detail` · `example` · `caution` · `seen_in`(실제 어느 공고에서 봤는지) ·
`verified`(원문 검증 여부)를 붙였다.

```json
{
  "term": "이차보전",
  "aliases": ["이자차액보전", "이차차액보전", ...],
  "easy": "은행 대출 이자 중 일부를 시청이 대신 내주는 것.",
  "caution": "'지원금 3천만원'처럼 현금을 주는 사업과 완전히 다르다.
              대출 심사에 떨어지면 이 사업도 받을 수 없다.",
  "seen_in": "2026년 화성시 소상공인 자금지원사업 (화성시 공고 제2026-442호)",
  "verified": true
}
```

- `find_terms()` 는 **긴 표기를 먼저 맞춘다** — 「고시공고」가 「공고」로 잘리지 않게.
- 공고 상세 화면에서 사전에 있는 낱말에 점선 밑줄이 붙고, 그 위에서 뜻이 열린다.

### 4-2. RAG — 임베딩이 아니라 키워드를 썼다

**같은 LLM · 같은 5개 질문**으로 4가지 검색 방식을 직접 비교했다 (`llm/report/`).

| 방식 | Hit@1 | Hit@3 | MRR | 코퍼스 인코딩 |
|---|---|---|---|---|
| **키워드 substring** | **1.000** | 1.000 | 1.000 | **0ms** |
| BGE-M3 | 0.800 | 1.000 | 0.900 | 2,129ms |
| KoSimCSE-RoBERTa | 0.800 | 0.800 | 0.800 | 172ms |
| KR-SBERT | 0.800 | 0.800 | 0.800 | 158ms |
| KURE-v1 | 오류 | — | — | — |

**결정적 사례 (F3-03).** 질문: "화성시 소상공인 자금지원사업 금리가 정확히 몇 %예요?"

| | 키워드 RAG | BGE-M3 |
|---|---|---|
| 검색 1위 | `소상공인` (직접 매칭) | `미소금융` (의미 유사) |
| LLM 답변 | "공고 또는 담당 기관에 확인 필요" | **"연 1.5%~3.5%"** ← 환각 |

BGE-M3는 "소상공인 금리"와 의미가 가장 가까운 **미소금융**을 가져왔는데, 미소금융 항목에는
금리가 적혀 있어서 LLM이 그걸 화성시 사업 금리로 옮겨 썼다.
**검색이 더 그럴듯할수록 환각이 더 위험해진다**는 사례다.

> **한 줄 정리:** 코퍼스가 57개 전문 용어라 사용자가 그 단어를 직접 말한다.
> 이 조건에서는 키워드가 정확도도 높고 환각에도 안전했다.
> 코퍼스가 수천 개로 늘면 BGE-M3로 바꿀 준비는 돼 있다.

### 4-3. RAG가 실제로 필요하다는 증거 (방금 배포 서버에서 확인)

RAG 없이 같은 모델에 「이차보전이 무슨 뜻이에요?」를 물었더니:

> "이차보전은 '이차(二次)'와 '보전(補償)'이 결합된 말로, 정부가 사업으로 발생한
> **2차적인 손실**을 보전해 주는 제도를 의미합니다…"

**완전히 틀렸다.** 이차보전은 이자 차액을 대신 내주는 제도다.
사전 57항목을 붙이면 이 답이 나오지 않는다.

### 4-4. LLM 호출 (`api/llm.py`)

- 프론트 → `POST /api/llm` → 서버가 공급자를 고른다. **키는 서버에만.**
- 우선순위 **Groq → xAI → Gemini**. 한 곳이 실패하면 다음으로 넘어간다.
- 한 공급자 안에서도 `GROQ_API_KEY`, `GROQ_API_KEY_2`, `GROQ_API_KEY_3` 순으로 **키를 갈아탄다**
  (한도 초과 대비). 현재 Groq 키 2개 + Gemini 키 1개.
- **`temperature = 0` 고정.** 같은 입력에 같은 출력이 나와야 벤치마크 비교가 성립한다.
- JSON 모드일 때 프롬프트에 "json"이라는 낱말이 없으면 OpenAI 형식 API가 400을 돌려준다.
  없으면 서버가 넣어준다 — 이것 없이 배포하면 **서류 체크리스트가 통째로 실패**한다.

**현재 실제 사용 모델: `openai/gpt-oss-120b` (Groq).**
`llm/report/`의 벤치마크는 `llama-3.3-70b-versatile`로 돌렸다. 모델이 바뀐 뒤 재측정은 안 했다.
질문 들어오면 **그대로 말할 것.**

## 5. 세무일정 (`policy_data/tax_schedule.py` + `tax_calendar.json`)

- **국세청 원문 대조 14건.** 각 항목에 `source`(예: "부가가치세법 제49조")와 `verified` 표시.
- 항목마다 `applies_to` — `entity_type`(개인/법인) · `vat_type`(일반/간이) · `has_employee`.
  **프로필에 답이 없으면(`null`) 걸러내지 않는다.** 모른다는 이유로 빼면 신고를 통째로 놓친다.

### 법정기한을 그대로 띄우면 틀린다

국세청 규정: *"신고기한이 공휴일·토요일인 경우 그 다음 날을 신고기한으로 한다."*
그래서 주말·공휴일을 넘겨 **실제 기한**을 계산한다.

2026년 실측:

| | 개수 |
|---|---|
| 등록 일정 | 14건 (고정일자 13 + 매월 반복 1) |
| 고정일자 일정 중 **밀리는 것** | **13건 중 9건** |
| 서로 다른 법정기한 날짜 | 10개 |
| 그중 **밀리는 날짜** | **6개** |

예: 종합소득세 **5/31(일) → 6/1**, 부가세 2기 확정 **1/25(일) → 1/26**,
부가세 1기 확정 **7/25(토) → 7/27**.

> **발표에서 숫자를 말할 때 기준을 붙일 것.**
> "일정 13건 중 9건이 밀린다"(일정 기준)와 "날짜 10개 중 6개가 밀린다"(날짜 기준)는
> 둘 다 맞지만 **다른 걸 세고 있다.** 기준 없이 말하면 반박당한다.

**약점:** 공휴일은 해마다 손으로 넣는다(설날·추석이 음력이고 대체공휴일 규칙이 있어서).
**2027년이 아직 안 들어가 있다.** 연말이 되면 그 해는 주말만 반영된다.
화면에 경고 배너가 뜨도록은 해뒀다.

## 7. 인증 · 저장

- **카카오 OAuth.** 프론트는 인가 코드만 받아 서버로 넘기고, 서버가
  `code → 액세스 토큰 → 사용자 정보 → 우리 JWT` 순서로 처리한다.
  `client_secret`은 서버에만 있다.
- **JWT는 표준 라이브러리로 직접.** HS256이면 `hmac`+`hashlib`로 충분하다.
  서명 검증은 반드시 `hmac.compare_digest` — `==`로 비교하면 실행 시간 차이로
  서명을 한 바이트씩 맞춰볼 수 있다(타이밍 공격). 유효기간 2주.
- **Supabase**에는 프로필과 온보딩 답변만 저장한다. `service_role` 키는 서버 전용.
- **탈퇴(`DELETE /api/users/me/onboarding`)** 를 넣어서 온보딩을 통째로 지울 수 있다.
  로컬 `mars-fit-*` 키도 같이 지운다.
- 사업자등록증 이미지·사용자 프로필은 **저장소에 절대 올리지 않는다**(`.gitignore`).

**OCR (`backend/OCR.py`)** — 사업자등록증에서 상호·업종·개업일을 뽑는 코드는 있지만
**Vercel에서는 안 돈다.** EasyOCR이 torch를 끌고 오는데 함수 용량 한도를 넘는다.
`/api/health` 가 `"ocr": "미지원"` 이라고 정직하게 돌려준다.
**"OCR 됩니다"라고 말하지 말 것.** 로컬 서버에서만 시연 가능하다.

## 9. 오늘(8/20) 자동 갱신이 실패한 이유

**기업마당 API가 GitHub Actions 러너에서 응답하지 않았다. 우리 코드 문제가 아니다.**

근거:

| | |
|---|---|
| 실패 단계 | 「공고 수집·추출·검사」 — 즉 **1/5 수집에서 멈췄다** |
| 걸린 시간 | **333초** |
| `collect.py` 재시도 예산 | 60초 타임아웃 × 4회 + 대기 15+30+45초 = **330초** |
| 정상 실행(8/18) 전체 시간 | 244초 — **성공하는 게 실패보다 빨랐다** |

333초는 "다 실패하고 포기하는 데 걸리는 시간"과 정확히 맞는다.
코드 주석에도 이미 적혀 있다 — *"기업마당은 해외 IP에서 자주 끊긴다.
GitHub Actions 러너(Azure US/EU)에서 타임아웃이 났고, 같은 시각 국내 서버에서는
0.15초에 응답했다."* 8/17에도 같은 이유로 한 번 실패해서 재시도 로직을 넣었는데,
이번엔 **4번을 다 써도 안 붙었다.**

**확인한 것:** 방금 이 서버(국내)에서 수집 → 첨부 → 추출 → 검사 → guard 를
**캐시 없이 처음부터** 돌렸다. 전부 통과했고 결과도 지금 배포본과 같은 **59건, 오류 0**이다.
**데이터에는 아무 이상이 없다. 발표에 영향 없다.**

**고치려면** (지금은 하지 말 것 — 발표 후):
- 재시도 횟수·대기를 늘린다 (4회 330초 → 6회 이상)
- 수집 실패는 **실패가 아니라 건너뛰기**로 처리한다 (전날 데이터를 그대로 둔다)
- 또는 국내에서 도는 러너/서버에서 수집한다

# 예상 질문 —— 답변 포함

## A. 기술 구조

**Q. AI를 어디에 썼나요? 그냥 필터링 아닌가요?**
> 두 군데에 나눠 썼고, **일부러 나눴습니다.**
> 자격 판정과 점수는 **규칙 기반**입니다. "당신은 대상이 아닙니다"라는 말은 재현 가능하고
> 근거를 댈 수 있어야 하기 때문입니다. LLM에 맡기면 같은 질문에 다른 답이 나옵니다.
> 반면 **어려운 말을 풀어주는 대화**는 LLM+RAG로 했습니다. 여기는 표현이 다양해야 좋습니다.
> **판정은 규칙, 설명은 LLM** — 이게 저희 설계 원칙입니다.

**Q. 왜 파인튜닝을 안 했나요?**
> 학습 데이터가 없습니다. 화성시 소상공인 공고는 59건이고, 이걸로 파인튜닝하면
> 과적합만 됩니다. 대신 **57항목 사전을 검증해서 RAG로 넣는 쪽**에 시간을 썼고,
> 그게 환각을 실제로 막았습니다(F3-03 사례).

**Q. LLM 응답이 느리거나 실패하면요?**
> 세 단계로 막았습니다. ① 공급자 3곳(Groq → xAI → Gemini) 순차 폴백,
> ② 같은 공급자 안에서 API 키를 여러 개 순차 사용, ③ JSON 파싱이 실패해도
> 원문 텍스트를 그대로 답변으로 내보냅니다.
> **다만 시연 영상에서 실제로 한 번 실패했습니다.** 숨기지 않겠습니다 — 2차에서 보완합니다.

**Q. 왜 서버리스인가요? 서버를 두면 안 되나요?**
> 팀이 3명이고 대회 기간이 짧습니다. 서버를 두면 누군가 그걸 계속 지켜야 합니다.
> 공고 데이터는 하루 한 번 바뀌는 읽기 전용이라 배포에 같이 실으면 됩니다.
> **운영 부담을 0으로 만드는 게 이 규모에서는 기능보다 중요했습니다.**

**Q. 외부 라이브러리가 하나도 없다는 게 사실인가요?**
> 파이썬 쪽은 사실입니다. `requirements.txt`가 없습니다. JWT는 `hmac`으로 직접 만들었고,
> Supabase는 PostgREST를 `urllib`로 부릅니다. Vercel 함수 용량 제한 때문이었는데,
> 결과적으로 콜드스타트가 빨라졌습니다.

## B. 데이터

**Q. 공고 데이터는 어디서 오나요? 직접 입력하나요?**
> **기업마당 공공 API**입니다. 매일 아침 6시에 GitHub Actions가 자동으로 받아옵니다.
> 사람이 손대지 않습니다. 원본 1,551건 중 소상공인·화성시민 조건으로 걸러 59건입니다.

**Q. 59건밖에 안 되나요? 너무 적은데요.**
> 전체 공고는 1,551건이지만, **화성시민인 소상공인이 실제로 신청할 수 있는 것**이
> 63건입니다. 저희는 그중 59건을 담았습니다. 커버리지 94%입니다.
> 숫자를 부풀리려면 전국 공고를 다 넣으면 되는데, 그러면 신청도 못 하는 걸 보여주게 됩니다.

**Q. 1,551건에서 59건까지 어떻게 줄어드나요? 너무 많이 버리는 것 같은데요.**
> 네 단계입니다. ① 소상공인 사업만 남기면 **280건**, ② 그중 화성시민이 실제로 신청할 수
> 있는 것만 남기면 **63건**, ③ 마감된 것 제외, ④ 공고가 스스로 소상공인은 대상이 아니라고
> 적은 4건 제외 → **59건**입니다.
> **가장 크게 빠지는 곳은 ②지역입니다. 280건 중 217건이 다른 지역 전용입니다** —
> 경북 34, 서울 19, 강원 19… 경기도 안에서도 시흥·양주·포천 전용이 있습니다.
> 화성시민은 그걸 신청할 수 없습니다. 숫자를 키우려면 다 넣으면 되지만,
> 그러면 신청도 못 하는 공고를 보여주게 됩니다.

**Q. 63건 중 4건은 왜 뺐나요? 임의로 고른 건 아닌가요?**
> **공고가 스스로 "소상공인은 대상이 아니다"라고 적은 것만** 뺐습니다. 네 건입니다.
> 하나는 공고문에 「소기업(소상공인)은 지원 제외」가 명시돼 있었고,
> 나머지 셋은 **농업인 둘·재직자 하나** — 업종이 아니라 신분이 아예 다른 사업입니다.
> 판단이 애매한 건 빼지 않고 **「확인필요」로 남깁니다.** 저희 원칙은 "모르면 남긴다"입니다.
> 실제로 반대로 하다가 사고가 났었습니다 — 접수기간을 못 읽었다는 이유로 30건을
> 잘라내고 있었는데, 그 안에 폐업·재기 지원처럼 제일 급한 것들이 들어 있었습니다.

**Q. 공고문을 정말 다 읽나요?**
> **아니요. 59건 중 29건입니다.** 나머지는 첨부가 구형 HWP이거나 스캔 이미지 PDF라
> 텍스트를 못 뽑습니다. 그 30건은 API 요약으로 처리하고,
> **요건을 못 읽었다는 사실을 화면에 「확인필요」로 표시합니다.** 100점을 주지 않습니다.

**Q. 잘못된 정보를 보여줄 위험은요?**
> 그래서 세 가지를 했습니다.
> ① 확실한 것만 「불충족」으로 자릅니다. 애매하면 「확인필요」로 남깁니다.
> ② 서류는 **원문에서 확인한 것(120개)과 추정한 것(74개)을 구분해서** 표시합니다.
> ③ `guard.py`가 매일 "데이터가 줄지 않았는지"를 검사해서, 파이프라인이 조용히
> 망가지는 걸 막습니다. 실제로 8월 17일에 그렇게 데이터가 깎인 적이 있어서 만들었습니다.

**Q. 공고가 마감되면요?**
> 매일 갱신되고, 마감일이 지난 건 자동으로 빠집니다.
> 접수기간이 "예산 소진시까지"처럼 문구로 적힌 것은 **원문 문구를 그대로 보여줍니다.**
> "신청기간 해석 필요"보다 "예산 소진시까지"가 사장님에게 쓸모 있기 때문입니다.

## C. AI / RAG

**Q. 왜 임베딩을 안 쓰고 키워드를 썼나요? 기술적으로 후퇴 아닌가요?**
> 실험으로 결정했습니다. 같은 LLM, 같은 5개 질문으로 4가지 방식을 비교했고
> **키워드가 Hit@1 1.000, BGE-M3가 0.800**이었습니다.
> 더 중요한 건 환각입니다. BGE-M3는 "소상공인 금리" 질문에 의미가 가까운 **미소금융**을
> 가져왔고, LLM이 미소금융 금리를 화성시 금리로 답했습니다. 키워드는 "확인이 필요하다"고
> 답했습니다. **코퍼스가 57개 전문 용어라 사용자가 그 단어를 직접 말합니다.**
> 코퍼스가 수천 개로 늘면 임베딩으로 바꿉니다. 스크립트는 이미 있습니다.

**Q. 어떤 모델을 쓰나요?**
> 현재 배포는 **Groq의 gpt-oss-120b**이고, temperature는 0으로 고정했습니다.
> 다만 **벤치마크는 llama-3.3-70b로 돌렸고 모델 교체 후 재측정은 못 했습니다.**
> 그 부분은 정직하게 말씀드립니다.

**Q. RAG가 정말 효과가 있나요?**
> 방금 배포 서버에서 확인한 예를 하나 들겠습니다.
> 사전 없이 「이차보전이 뭐예요」를 물으면 모델이 **"2차적인 손실을 보전하는 제도"**라고
> 답합니다. 완전히 틀렸습니다. 실제로는 대출 이자 차액을 시가 대신 내주는 제도입니다.
> 사전을 붙이면 이 답이 나오지 않습니다. **소상공인에게는 이 한 줄 차이가 대출을 받느냐
> 마느냐입니다.**

**Q. 용어 사전 57개는 누가 만들었나요? 신뢰할 수 있나요?**
> 실제 화성시·경기도 공고문에서 뽑아 손으로 썼습니다. 항목마다 **어느 공고에서 봤는지**(`seen_in`)와
> **원문 검증 여부**(`verified`)를 기록했습니다. 검증 안 된 항목은 챗봇 답변에
> "접수 기관에 한 번 더 확인해 주세요"라는 경고가 자동으로 붙습니다.

## D. 보안 · 개인정보

**Q. API 키는 어떻게 관리하나요?**
> 전부 서버(Vercel 환경변수)에만 있습니다. 프론트에서 LLM을 직접 부르지 않고
> `/api/llm`으로 우회하는 이유가 그것입니다.
> Vite의 `VITE_` 환경변수는 번들에 평문으로 박히는데, 저희도 초기에 테스트 키를 넣고
> 빌드했더니 **번들 JS에 3번 노출됐습니다.** 그걸 보고 구조를 바꿨습니다.

**Q. 개인정보는요?**
> 저장하는 건 온보딩 답변(나이대·업종·지역 등)뿐입니다. Supabase에 들어가고
> `service_role` 키는 서버 전용입니다. 사업자등록증 이미지나 실명은 **저장소에도, DB에도
> 올리지 않습니다.** 탈퇴 기능으로 온보딩을 통째로 삭제할 수 있습니다.

**Q. JWT를 직접 구현했다고요? 안전한가요?**
> HS256만 쓰는 조건이면 `hmac`+`hashlib`로 충분하고, 표준 구현과 동일합니다.
> 서명 비교는 `hmac.compare_digest`로 합니다 — `==`로 비교하면 타이밍 공격이 가능합니다.
> 알고리즘은 서버에서 고정해서 `alg: none` 공격도 막았습니다.

## E. 운영 · 확장

**Q. 다른 시·군에도 쓸 수 있나요?**
> 지역 판정이 `scope()` 함수 한 곳에 모여 있고, 공고 필터도 설정에 가깝습니다.
> 다른 시로 옮기려면 **지역 이름과 상권 CSV만 바꾸면 됩니다.**
> 다만 화성시 전용 공고(고시공고 크롤러)는 그 시에 맞게 다시 만들어야 합니다.

**Q. 사용자가 늘면 비용은요?**
> 매칭은 서버리스 함수 안에서 끝나고 외부 호출이 없어서 비용이 거의 안 붙습니다.
> LLM만 호출당 비용이 있는데, 현재는 무료 한도 안이고 키를 여러 개 돌려 씁니다.

**Q. 지금 안 되는 게 뭔가요?**
> §11에 정리해뒀습니다. **먼저 말하는 게 낫습니다.**

## F. 서비스 / 사업성

**Q. 기존 기업마당·소상공인마당과 뭐가 다른가요?**
> 기존 사이트는 **목록**을 줍니다. 사장님은 1,551건 앞에서 "내가 되는 게 뭐지"를
> 스스로 판단해야 합니다. 저희는 질문 8개를 받고 **"당신은 이 10건"**이라고 말합니다.
> 그리고 거기서 끝나지 않고 **서류를 어디서 떼는지, 수수료가 얼마인지, 어느 사이트로
> 가야 하는지**까지 데려다줍니다. 정보 제공이 아니라 **신청 동행**입니다.

**Q. 왜 소상공인인가요?**
> 지원사업이 없어서 못 받는 게 아니라, **있는 줄 몰라서 못 받습니다.**
> 그리고 저희가 흘리고 있던 30건을 찾아보니 폐업·재기·고용보험료·체납 구제였습니다.
> 제일 급한 사람이 제일 못 찾고 있었습니다.

**Q. 앞으로 계획은요?**
> ① 챗봇 안정화, ② 아파트·유동인구 실데이터 연동, ③ 마감 알림(카카오 알림톡),
> ④ 코퍼스가 커지면 임베딩 RAG로 전환. 순서까지 정해뒀습니다.
